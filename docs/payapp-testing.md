## 2026-11-13 운영 연결 준비 결과 (이 절이 이전 상태보다 우선)
- 기존 4개 Secrets 이름 존재 확인, 값 출력·변경 없음. API HTTPS 접속 200은 확인했으나 개별 계정의 정기결제 제한 여부를 증명하지 않는다.
- 공식 https://www.payapp.kr/homepage/api/api.html 에 ‘별도 승인절차 없이 가입만 하면 바로 연동작업이 가능합니다’가 명시됨을 재확인했다. 이전 별도 승인 증빙 요구와 PAYAPP_REBILL_APPROVED 차단을 제거했다. 가맹점 승인은 사용자가 완료했다고 알렸으며 별도의 API 승인서를 요구하지 않는다.
- DB 확인: 기존 billing_keys 0건, 유료 active 구독 0건, 페이앱 실결제 0건. cron에는 문자 알림·견적 정리만 있고 구독 청구 작업은 없다. 기존 체험 만료일과 고객/견적 기록은 변경하지 않았다.
- 공식 https://docs.payapp.kr/dev_center01.html 최신 조회: rebillRegist → 구매자 최초 승인 → 다음 주기 제공자 자동결제. billRegist는 변경/이용불가 예고로 사용하지 않는다. rebillCancel은 다음 청구를 중단하며 해지는 되돌릴 수 없다.
- 공식 문서에 rebillCycleMonth=1~31 또는 90(매월 말일), rebillExpire=yyyy-mm-dd 필수는 확인된다. 29~31일의 짧은 달 처리, 요청일/승인일 차이의 변경 방법, 만료 최대 기간·무기한 설정, 계정 권한을 조회하는 비청구 API는 확인되지 않았다. 90은 모든 달 말일이며 첫 승인일 29/30을 영구 말일로 바꾸는 것과 같지 않으므로 임의 적용하지 않는다.
- 운영 전 필요한 서버 설정: PAYAPP_MONTH_POLICY_CONFIRMED=true (제공자 갱신 정책 확인 후), PAYAPP_REBILL_EXPIRE (제공자가 허용한 실제 계약 만료일). 값은 임의로 만들지 않았고 미확인 시 요청 생성 자체가 차단된다. 기존 결제 Secrets는 다시 요청하지 않는다. 별도 API 승인 설정은 필요하지 않다.
- 비청구 계정 조회 검토: 공식 useridCheck는 대리점/리셀러 전용 아이디 중복 검사다. 일반 가맹점 값을 resellerid로 가장하지 않았고 이 기능을 정기결제 권한 조회로 오인하지 않는다. getNaverpayCashPrice는 실제 네이버페이 거래번호가 필요하므로 정기결제 상태 검사에 사용하지 않는다. 공개 문서에서 일반 가맹점 정기결제 권한을 확인하는 읽기 전용 API는 발견되지 않아 제한 있음/없음을 단정하지 않는다. 등록·해지·승인 API를 조회 목적으로 호출하지 않는다.
- 정정 후 비청구 점검: 기존 연동값 4개 런타임 존재 확인, 자격증명 없이 공식 API HTTPS 요청 200 및 URL-encoded state 응답 확인. 이는 계정 인증/정기결제 제한 확인을 의미하지 않는다. Vitest 34건 재통과, 본인 모바일 동의창에서 별도 승인 문구 제거와 두 미확인 조건만 표시, GET/POST 복귀/401 통보 차단 유지 확인. 실제 카드 청구·고객 문자·환불·실제 계정 강제 변경 0건.
- 기존 카드/화면 배치 보존, 모의 성공 버튼은 실제 가입 경로에서 제거. 로그인 ‘한 달 무료’는 ‘10일’로 통일. 오늘 30,000원·자동갱신·첫 성공 기준 다음 달·해지·취소/실패 체험 보존 고지 후 직접 동의한다.
- startPayappSubscription은 업체 연락처와 동의를 확인하고 잠금 RPC/열린 주문 고유 인덱스로 하나의 요청만 생성한다. 공급자 요청의 타임아웃·저장 실패는 잠금을 유지하여 임의 재요청하지 않는다. 기존 pending 결제창만 재사용한다. 생성 성공은 이용권이 아니다.
- 인증 통보는 linkkey/linkval/userid, responsedate와 hash 검증 → 주문 UUID/업체 UUID/정기번호/정확히 30,000원 비교 → 거래번호+상태 고유키와 DB 잠금 → 결제내역/구독 원자 저장. 카드번호/CVC 등 추가 필드는 파싱 결과와 DB에서 제외하고 요청 본문 로그를 남기지 않는다.
- 앱 자체 청구 작업은 없음. PayApp이 유일한 자동청구 주체. 첫 승인일과 요청일이 다른 경우 잘못된 주기를 유지하지 않도록 공급자 해지를 요청하고 이미 승인된 이용기간은 유지한다. 이는 날짜 정책 미확인 상태를 해결한 것이 아니며 운영 활성화 전 제공자 확인이 여전히 필요하다.
- 실패 통보는 성공 이용권을 부여하지 않음. 1회차 실패는 공식 문서상 Noti되지 않아 복귀는 확인 중/미승인으로 표시. 2회차 이후 pay_state=99 실패 내역을 기록한다. 승인취소/부분취소는 검토 상태로 분리한다. 실제 환불은 실행하지 않는다.
- GET/POST 복귀 모두 303으로 읽기 전용 /billing/payapp/return 이동. URL의 success/amount는 무시. 인증 복구 후 DB 읽기만 하며 pending은 최대 1분 폴링한다. 새 인앱 브라우저에 세션이 없으면 로그인 후 확인 안내, 유료권한 변경 없음.
- 기존 Toss 발급/청구 함수와 callback의 실제 호출을 차단. 기존 Secrets/기록은 보존.

## 페이앱 판매자가 준비할 설정
공식 문서: https://docs.payapp.kr/docs/05-subscription.md
통보 문서: https://docs.payapp.kr/docs/04-webhook.md
판매자 안내: https://www.payapp.kr/homepage/pay/pay_recurring.html

1. 판매자 아이디와 linkkey/linkval/requestkey는 PAYAPP_USER_ID, PAYAPP_LINK_KEY, PAYAPP_LINK_VALUE, PAYAPP_REQUEST_KEY로 보안 저장되어 있다. 이번 작업에서 값을 변경하거나 결제 요청에 사용하지 않는다.
2. **정기/등록결제 → 정기결제 등록**의 상품 기준은 ‘견적잇 업체 구독’, 30,000원, 월간이다. 운영 건을 지금 등록하지 않는다.
3. API 기준은 `goodprice=30000`, `rebillCycleType=Month`, 카드만이면 `openpaytype=card`, 자동 문자 금지는 `smsuse=n`. 월 결제일과 필수 종료일(`rebillExpire`)은 운영 정책 확정이 필요하다. 임의 종료일을 정하지 않았다.
4. 공식 공개 API에는 무청구 sandbox나 가입 후 10일 뒤 최초 청구를 보장하는 등록 옵션이 확인되지 않았다. 페이앱에 **무청구 시험 판매자/시험 카드 제공 여부**, **등록 시 최초 승인 없이 무료체험 종료 후 첫 청구 가능한 방식**을 먼저 확인한다. 즉시 승인되는 정기결제를 무료체험 중 호출하면 안 된다.
5. 페이앱 통보는 `userid/linkkey/linkval` 검증, 서버 주문의 금액·정기결제번호 비교, 거래번호(`mul_no`)별 중복 처리가 필요하다. 해지는 `rebillCancel`, 인증은 `requestdate`와 `sha256(userid + requestdate + requestkey)`를 사용한다.
6. 준비한 주소 (미게시):
   - feedbackurl: https://gyeonjeokit.lovable.app/api/public/payapp/feedback
   - returnurl: https://gyeonjeokit.lovable.app/api/public/payapp/return
   - 복귀 주소는 /billing/payapp/return 화면으로 이동하며 저장된 모의시험만 읽는다. URL의 성공/금액 주장은 무시하고 이용권을 변경하지 않는다.
   - 통보 주소는 현재 모든 통보에 503을 반환하고 저장·승인·이용권 변경을 하지 않는다. 공식 통보 인증 계약 미확인 상태에서 성공 응답하지 않는다. 아직 판매자 운영 설정에 등록하지 않는다.
7. 첫 운영 결제는 체험 중에도 가능하되 즉시 30,000원 청구·체험 종료·월 정기결제·다음 결제일을 고지하고 별도 동의 및 서버의 결제 성공 확인 뒤에만 유료 전환해야 한다. 다음 결제는 실제 첫 결제 성공일 한 달 뒤이며, 이전 체험 종료 청구 예약은 취소 확인 후 중복되지 않게 한다. 취소·실패 시 체험은 보존하고 미동의 이용자는 자동 청구하지 않는다. 현재 이 흐름은 계정별 모의시험만 구현되어 실제 동의/주문/거래/이용권 전환과 외부 예약 취소는 미구현이다.
8. 운영 연결 전 공식 통보 인증·재시도/응답 규약을 확인하고, 인증된 서버 거래 조회·주문 금액/업체/정기번호 대조·거래번호 고유 제약을 통한 원자적 1회 이용권 반영을 구현해야 한다. 기존 모의시험 중복 처리를 운영 결제 검증으로 간주하지 않는다.

현재 이 작업으로 기존 토스 정기결제 계약을 자동 취소하거나 페이앱으로 이전하지 않는다. 기존 정기결제 계약이 있다면 별도 확인과 중복 청구 방지 전환이 필요하다.
